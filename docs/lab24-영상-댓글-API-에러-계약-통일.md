# lab24 — 새 댓글 화면이 오류를 못 살린다: 영상 댓글 API 에러 계약 통일

- 분야: 스프링 MVC · 유형: 변형복습 · 난이도: 응용
- 패키지: `com.vryez.backendlab.lab24`
- 예상 소요: 1~2시간

## 배경 시나리오

동영상 게시판에 **영상 댓글 등록 API**를 얹었는데, 앱 팀에서 버그 리포트가 올라왔다. 새 댓글 작성 화면이 실패했을 때 사용자에게 알맞은 메시지를 못 띄운다는 것이다. 원인을 까 보니 우리 API가 오류마다 **제각각 다른 모양**으로 응답하고 있었다.

- 내용을 비운 채 보내면(검증 실패) 스프링 부트 기본 400 JSON이 오는데, 어떤 필드가 왜 틀렸는지 앱이 파싱할 구조가 없다.
- 요청 바디 JSON이 중간에 끊기면(깨진 요청) 또 다른 400 포맷이 온다.
- 주소창의 영상 번호 자리에 숫자가 아닌 값이 들어오면 역시 다른 400이 온다.
- **없는 영상**에 댓글을 달면 `500 Internal Server Error`가 떨어진다. (없는 리소스인데 서버 장애로 보인다.)
- **댓글이 잠긴 영상**(비공개/사내 교육본)에 달아도 그냥 500이 난다.

앱 팀의 요구: "성공이든 실패든 **똑같은 한 가지 에러 계약**으로 내려달라." 오류 종류를 코드로 구분할 수 있어야 하고, 검증 실패일 때는 **어떤 필드가 왜 틀렸는지 목록**으로 받아야 화면 각 입력칸 아래에 빨간 메시지를 띄울 수 있다.

## 요구사항

컨트롤러의 정상 로직은 그대로 두고, **전역 예외 처리를 새로 얹어** 모든 실패를 하나의 계약으로 통일한다.

스캐폴드에는 컨트롤러·요청 DTO·인메모리 저장소·커스텀 예외까지 준비돼 있다. **네가 만들 것은 두 개다:**

- `web/ErrorResponse.java` — 에러 응답 DTO
- `web/ApiExceptionAdvice.java` — `@RestControllerAdvice` 전역 예외 처리기

시드 데이터: 영상 1·2(댓글 열림), 영상 3(댓글 잠김), 그 외 번호는 없는 영상.

## 완료 조건

엔드포인트: `POST /lab24/videos/{videoId}/comments`, 요청 바디 `{ "author": "...", "content": "..." }`

**성공** — 유효한 요청(존재하고 댓글이 열린 영상)은 `201 Created`로 생성된 댓글(`id`, `videoId`, `author`, `content`, `createdAt`)을 반환한다.

**실패는 아래 단일 에러 계약으로 통일**한다. 최상위 필드는 항상 `code`(문자열), `message`(문자열), `errors`(배열, 필드 오류가 없으면 빈 배열) 세 가지다.

```json
{
  "code": "VALIDATION_ERROR",
  "message": "요청 값이 올바르지 않습니다",
  "errors": [
    { "field": "content", "reason": "댓글 내용은 비어 있을 수 없습니다" }
  ]
}
```

오류 종류별 매핑:

| 상황 | HTTP 상태 | `code` | `errors` |
|---|---|---|---|
| `@Valid` 검증 실패 | 400 | `VALIDATION_ERROR` | 위반한 필드마다 `{field, reason}` 1건씩 |
| 요청 바디 JSON이 깨짐 | 400 | `MALFORMED_JSON` | 빈 배열 |
| 경로변수 `videoId` 타입 불일치(숫자 아님) | 400 | `TYPE_MISMATCH` | 빈 배열 |
| 존재하지 않는 영상 | 404 | `VIDEO_NOT_FOUND` | 빈 배열 |
| 댓글이 잠긴 영상 | 409 | `COMMENTS_DISABLED` | 빈 배열 |

- 모든 실패 응답이 위 세 가지 최상위 필드를 **똑같이** 가진다(모양이 하나여야 한다).
- 없는 영상·잠긴 영상은 더 이상 500이 아니다.
- 검증 규칙: `author` 필수·최대 30자, `content` 필수·최대 500자. 두 필드가 동시에 틀리면 `errors`에 2건이 담긴다.

## 제약

- 스캐폴드 파일(컨트롤러, 저장소, DTO, 예외)은 수정하지 않는 것이 원칙이다. 예외 처리는 전부 새로 만드는 두 파일에서 해결한다.
- DB는 쓰지 않는다 — 저장소는 인메모리다.
- Spring Boot 4.1 / Java 21 기준: 검증은 `jakarta.validation.*`, 스프링 예외는 `org.springframework.*` 패키지의 것을 쓴다.
