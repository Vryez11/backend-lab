# lab23 — 프론트가 우리 API 에러를 파싱하지 못한다

- **분야**: 스프링 MVC / **유형**: 구현 / **난이도**: 응용
- **패키지**: `com.vryez.backendlab.lab23`
- **예상 소요**: 1~2시간

## 배경 시나리오

동영상 게시판 API가 프론트엔드 팀에서 반려됐다. 프론트가 보낸 버그 리포트:

> "성공 응답은 우리가 정한 스펙대로 잘 오는데, **에러 응답이 케이스마다 모양이 다 다릅니다.** 어떤 건 `timestamp`/`path`/`trace`가 붙은 스프링 기본 에러가 그대로 오고, 어떤 건 필드 오류 정보가 아예 없어서 어느 입력이 틀렸는지 화면에 못 띄웁니다. 게다가 **존재하지 않는 영상을 조회하면 404가 아니라 500이 떨어져서** 우리 쪽 전역 에러 핸들러가 '서버 장애'로 오인하고 사용자에게 장애 팝업을 띄웁니다. 에러 응답 스펙을 **하나로 통일**해 주세요."

## 요구사항

이 API의 모든 에러 응답을 **단일 포맷의 JSON 봉투(envelope)**로 통일한다.
**컨트롤러 코드에는 손대지 말고**(정상 흐름과 예외 처리의 분리), 전역 예외 처리 계층을 새로 만들어 아래 실패 상황들을 각각 올바른 상태 코드와 통일된 형식으로 내려준다.

- 없는 영상 조회 → **404**
- 요청 바디 검증 실패(제목 누락, 재생시간 음수 등) → **400** (어느 필드가 왜 틀렸는지 포함)
- 깨진 JSON 바디 → **400**
- 경로 변수 타입 불일치(`GET /lab23/videos/abc`) → **400**
- 그 외 예상치 못한 서버 오류 → **500** (내부 정보 노출 없이 간결한 메시지)

## 완료 조건

1. **에러 봉투 통일** — 모든 에러 응답은 다음 JSON 형태를 가진다. 상황과 무관하게 키 구성이 동일하다.

   ```json
   {
     "code": "VALIDATION_ERROR",
     "message": "입력값이 올바르지 않습니다.",
     "fieldErrors": [
       { "field": "title", "reason": "제목은 비어 있을 수 없습니다." }
     ]
   }
   ```

   `fieldErrors`는 필드 단위 오류가 없는 경우 **빈 배열 `[]`**로 내려온다(키 자체는 항상 존재).

2. **상태 코드·코드값 매핑**

   | 상황 | HTTP 상태 | `code` |
   |---|---|---|
   | 존재하지 않는 영상 조회 | 404 | `VIDEO_NOT_FOUND` |
   | 바디 검증 실패(`@Valid`) | 400 | `VALIDATION_ERROR` |
   | 역직렬화 불가(깨진 JSON) | 400 | `MALFORMED_REQUEST` |
   | 경로/파라미터 타입 불일치 | 400 | `TYPE_MISMATCH` |
   | 예상치 못한 서버 오류 | 500 | `INTERNAL_ERROR` |

3. **검증 실패 시** `fieldErrors`에 위반된 **모든** 필드가 담긴다(한 요청에 제목·재생시간이 동시에 틀리면 2건 모두).

4. **정보 노출 금지** — 어떤 에러 응답에도 스프링 기본 필드(`timestamp`, `path`, `trace`, `exception`)가 포함되지 않는다. 특히 500 응답의 `message`에 예외 메시지·스택 내용을 그대로 담지 않는다(고정된 일반 메시지).

5. **관심사 분리** — 예외 처리 로직은 각 컨트롤러 메서드 안의 `try/catch`가 아니라 전역 예외 처리 계층에 위치한다. 컨트롤러의 정상 경로 코드는 예외 처리 코드와 섞이지 않는다.

6. **회귀 없음** — 정상 조회(`GET /lab23/videos/1`)와 정상 생성(`POST /lab23/videos`)은 기존처럼 2xx로 동작한다.

## 제약

- 심어진 4개 파일(`VideoApiController`, `VideoCreateRequest`, `VideoResponse`, `VideoNotFoundException`)은 수정하지 않는다.
- `application.properties`의 `server.error.*` 옵션으로 해결하지 않는다 — 전역 예외 처리 계층이 응답 형식을 전담한다.
- 추가 의존성 불필요(webmvc + validation으로 충분). H2 테이블 불필요.

## 현재 상태 (시작점)

앱은 정상 기동되며, 전역 예외 처리 계층이 없어서 에러가 스프링 기본 형식(케이스마다 제각각)으로 나가는 상태다. 직접 띄워서 위 실패 상황들을 호출해 보고 시작하는 것을 추천.
