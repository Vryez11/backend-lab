# lab02 — 스프링 컨테이너 없이는 죽는 결제 서비스

- **유형**: 디버깅
- **난이도**: 기초
- **예상 소요 시간**: 30~60분
- **패키지**: `com.vryez.backendlab.lab02`

## 배경 시나리오

결제/주문 모듈에 `OrderService`가 있다. 이 서비스는 할인 정책(`DiscountPolicy`)과 주문 저장소(`OrderRepository`)에 의존해 결제 금액을 계산하고 저장한다.

팀은 CI에서 빠르게 돌릴 수 있도록, **스프링 컨테이너를 띄우지 않고** 계산 로직만 검증하는 순수 단위 테스트를 붙이려 했다. 그런데 이상한 일이 벌어진다:

- `OrderServiceUnitTest` — 테스트에서 `OrderService`를 직접 생성(`new`)해 메서드를 호출하는 순간 **`NullPointerException`이 터진다.**
- `OrderServiceIntegrationTest` — 같은 로직을 `@SpringBootTest` 통합 테스트로 돌리면 **멀쩡히 통과한다.**
- 앱도 정상 기동한다.

## 미션

"앱 실행·통합 테스트는 되는데 순수 단위 테스트만 죽는" 이 모순의 원인을 진단하고, **스프링 없이도** `OrderService`를 생성해 테스트할 수 있도록 설계를 고쳐라.

원인을 말로만 설명하는 게 아니라, **통과하는 순수 단위 테스트로 증명**해야 한다.

## 요구사항

1. 스프링 컨테이너 없이(순수 JUnit) `OrderService`를 생성해 할인 계산을 검증하는 단위 테스트가 통과한다.
2. 기존 통합 동작(앱 정상 기동 + 실제 주입)도 그대로 유지된다.
3. `OrderService`는 일단 생성된 뒤에는 의존 대상이 바뀔 수 없어야 한다(불변).

## 완료 조건

1. 스프링 컨테이너 없이 `OrderService`를 직접 생성하는 순수 JUnit 단위 테스트가 `NullPointerException` 없이 통과한다.
2. 애플리케이션이 정상 기동하고, 통합 실행에서 10,000원 주문에 할인 정책이 적용된 금액(**9,000원**)이 반환된다.
3. `OrderService`의 의존관계는 객체 생성 시점에 주입되며, 생성 이후에는 외부에서 교체·재설정할 수 없다(불변).
4. 의존관계 주입을 누락하면 실행 시점(런타임)이 아니라 **컴파일 시점**에 드러난다.

## 제약

- 단위 테스트에 `@SpringBootTest`를 붙여 "스프링 없이"라는 조건을 우회하는 것은 금지.
- `RateDiscountPolicy`(10% 할인)와 `MemoryOrderRepository`의 동작 자체는 바꾸지 않는다.
- 추가 의존성 불필요 — 지금 있는 것으로 충분하다.
